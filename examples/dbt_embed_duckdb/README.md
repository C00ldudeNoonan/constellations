# dbt_embed_duckdb — stel embedded inside a dbt-duckdb DAG (#177 prototype)

This is the round-trip proof for the "dbt drives stel" integration (design
issue [#177]): a **single `dbt build`** runs a stel extraction model as a dbt
Python model, tests it with native dbt tests, and feeds it into a downstream dbt
SQL model — one DAG, one lineage graph, **no orchestrator**.

Unlike [`../dbt_consumer`](../dbt_consumer) (which reads stel tables as external
`sources` after a separate `stel run`), here stel runs *inside* dbt as native
dbt nodes generated by `stel codegen`:

```
models/stel/raw_invoices.py     ← extraction  (stel, no upstream)
models/stel/invoice_summary.py  ← transform   (reads raw_invoices via dbt.ref().pl())
models/stel/monthly_totals.py   ← transform
models/stel/schema.yml          ← fields + tests (generated)
models/marts/invoice_facts.sql    ← SQL: select ... from {{ ref('invoice_summary') }}
```

A single `dbt build` runs all three levels in dependency order —
**extraction → transform → SQL** — as one lineage graph. Every `ref()` works
across dbt and stel because the stel models are real dbt nodes.

The `models/stel/*.py` and `schema.yml` files are **generated** by
`stel codegen` from the stel project's YAML (the source of truth); they're
checked in so the example runs without the codegen step.

## How it works

`stel.dbt_embed.materialize()` reuses the standalone runner's single-model path
but swaps a `CaptureAdapter` in for the warehouse: stel does document discovery,
extraction, and (for `llm:` models) its response cache in-process, then hands dbt
the resulting frame. **dbt owns materialization, tests, docs, and lineage; stel
owns the unstructured→structured extraction.** No stel table or state is written
to the dbt database.

## Run it

From `examples/dbt_embed_duckdb/`:

```bash
# Seed sample documents into the colocated stel project (once)
uv run --project ../.. stel --project-dir ../invoice_pipeline seed --count 8

# (Re)generate the dbt nodes from the stel project's YAML
uv run --project ../.. stel --project-dir ../invoice_pipeline \
  codegen --output models/stel

# Install this dbt project's env (dbt-duckdb + editable stel) and build
uv sync
STEL_PROJECT_DIR="$(cd ../invoice_pipeline && pwd)" uv run dbt build --profiles-dir .
```

Expected: `PASS=14` — the extraction model, two transform models, ten schema
tests, and the SQL mart all succeed, materializing `raw_invoices`,
`invoice_summary`, `monthly_totals`, and `invoice_facts` into one
`target/embedded.duckdb`.

## Using this in your own dbt project

stel is **not** a dbt package — `packages.yml` / `dbt deps` can't install a
Python dependency, and the generated models `import stel`. It works through two
surfaces instead:

1. **Python package** — add `stel` (alongside `dbt-duckdb`) to your dbt
   project's environment (`pip install stel` / add it to `pyproject.toml`).
   This provides the `stel` CLI and the `stel.dbt_embed.materialize` engine
   the generated models call in-process. No extra is needed — `materialize`
   ships in the core install and has no dbt dependency.
2. **Generated dbt resources** — run `stel codegen --output models/stel`
   pointed at your stel project. It writes the Python-model shims + `schema.yml`
   into your dbt repo; commit them like any other model and regenerate when the
   stel YAML changes.

Then `dbt build` as usual (with `STEL_PROJECT_DIR` set). See the "Composing
with dbt → Embedded" section of the [main README](../../README.md) for the full
write-up.

## Prototype scope / caveats

- **dbt-duckdb only.** Python models on warehouse-side runtimes (Snowpark,
  BigQuery/Dataproc) sandbox network egress, so extraction backends that call
  Anthropic or read files can't run there. Other warehouses keep using the
  standalone CLI + `emit-dbt-sources` handoff.
- **Bidirectional `dbt_ref` source (now supported).** A stel transform can
  consume a **dbt-built** table by declaring `source: dbt_ref('<dbt_model>')`
  in its stel YAML:

  ```yaml
  # stel project: models/enriched_vendors.yml
  models:
    - name: enriched_vendors
      source: dbt_ref('vendor_dim')      # reads a dbt-built table
      transform: { type: python, module: transforms.enrich }
  ```

  `stel codegen` renders this into a literal `dbt.ref('vendor_dim')` in the
  shim, so dbt orders the dbt model first and `dbt docs` shows one lineage graph
  spanning both directions. These models run **only** in embedded mode — the
  standalone `stel run`/`build` rejects them, since only dbt can resolve the
  ref. A `dbt_ref` transform may also declare `depends_on:` for additional
  stel models in the same transform — see
  [`examples/dbt_ref_roundtrip_dbt`](../dbt_ref_roundtrip_dbt) for a runnable
  round trip proving the reverse direction end to end. One caveat: each
  generated shim resolves `STEL_PROJECT_DIR` as a single shared environment
  variable, so today one `dbt build` can embed models from only **one**
  stel project at a time.
- **No stel-side incremental** in embedded mode; the LLM response cache still
  makes re-runs cheap under dbt full-refresh.
- `STEL_PROJECT_DIR` locates the colocated stel project because dbt-duckdb
  copies Python models to a temp file (so `__file__` is unreliable); codegen will
  bake in a project-relative path.
